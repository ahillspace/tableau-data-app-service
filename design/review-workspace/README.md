# Architecture review workspace

This folder owns the editable review presentation and the standalone HTML package.
Authoritative architecture remains in the repository's planning and specification documents.
The presentation embeds the complete current document set from `../../specification.json` and distinguishes accepted policy, proposed mechanisms and missing runtime evidence.
Historical decision records are excluded from its sources.

## Edit and rebuild

Edit these presentation sources:

- [model.json](model.json) owns runtime positions and curated presentation relationships.
- [template.html](template.html) owns document structure.
- [template.css](template.css) owns the Terminal theme and responsive/print layout.
- [template.js](template.js) owns review interactions.
- [planning_model.py](planning_model.py) extracts authoritative module/policy content during the build.

The builder reads the architecture owner's planning sources on each run so generated module and decision excerpts cannot silently become a separate editable authority.
The document renderer uses pinned `marked@16.4.2` at build time only; the HTML requires no external library or network access.
Install the review tooling outside the specification repository:

```sh
npm install --prefix /tmp/review-workspace-browser --save-exact marked@16.4.2
REVIEW_MARKED=/tmp/review-workspace-browser/node_modules/marked python design/review-workspace/build.py
```

Run the build from the repository root.
`REVIEW_MARKED` may point to another installed copy of the pinned package.
The builder reads each manifest document into the HTML with its exact bytes and SHA-256, then renders readable Markdown and resolves internal document/heading links.
A missing required document or heading fails the build.
The result is a self-contained specification; the print view is a compact summary.
Do not edit [architecture-review.html](architecture-review.html) directly because it is generated by the builder.

## Reuse the review template

The first view is a short product overview followed by the complete PRD.
Keep the remaining views only when each answers a real review question.
Use stable component, module, flow, API, source and decision IDs across views.
Keep the same runtime topology while stepping through scenarios; highlight actual sender and receiver rather than rearranging the map on every step.
Every flow step separates data, authority, durable state and failure handling.
Every module exposes its owner, narrow interface, invariant, recovery boundary and extension path.
Every contract exposes caller authority, request, response and failure behavior.
Never encode a recommendation as an accepted requirement or present missing runtime evidence as document approval.
Place read-only accepted-policy summaries beside their context and link them from the accepted-decisions view.
Do not add approval pickers for settled policies; annotations can still target the stable content anchors.
Use stable `data-ohp-ref` values for annotation targets and ordinary IDs for navigation.

## Validate

The browser runner requires a local `playwright-core` installation and Chromium.
Set `REVIEW_PLAYWRIGHT` to its module path, then run `node design/review-workspace/check-ui.cjs`.
The runner captures every view at desktop, intermediate and narrow widths, compares the ordinary A39/F07 invocation with explicit A20/F04 Job admission, exercises every scenario step, opens all contracts and modules, verifies empty searches and embedded source documents, checks read-only accepted policies and retired routes, verifies every embedded source hash, and exports a nine-page review summary to PDF.
It expands each of the 28 source documents at 390px, verifies local code scrolling without page overflow, and exercises Enter/Space selection on diagram components and API rows while checking for JavaScript errors.
It also tests the document in a same-origin srcdoc iframe without publishing an Overhead.
The resulting validation record describes actual checks and their scope; the print summary omits repeated decision widgets and source snapshot bodies while retaining the overview and seven technical review topics.
Set `REVIEW_OUTPUT_DIR` to a task-private directory to keep new screenshots/PDF and validation reports outside the specification checkout; its default remains this directory.
Both browser runners support that output override, while always reading candidate/source files from this checkout.
Existing checked-in screenshots, shell reports and evidence manifest retain their historical scope; task-private reports identify the newly checked candidate hash.
The actual Overhead web-shell check is implemented in [check-ohp-shell.cjs](check-ohp-shell.cjs).
It loads the published head through the real local frontend/server, substitutes only the native desktop bridge's server discovery, verifies ordinary-capability versus explicit-Job navigation, all embedded source bytes/hashes, exact published-candidate equality and read-only accepted policies without staging feedback or using Send.
Its evidence distinguishes the web shell from the native Tauri application.
The standalone and readability checks apply to the rebuilt candidate.
No publication or live-shell run is part of this local document handoff.
Publication is separately owned; capture fresh shell evidence against its published head when the frontend is available.
Earlier shell reports and the evidence manifest identify their own previous head/hash and are historical until regenerated by their verification workflow.
The standalone check and the shell check validate the review document; they do not establish implementation or deployment of the proposed integration backend.

## Review delivery

This workspace does not publish itself.
After content review, the architecture owner can create or select the intended Overhead and load the packaged HTML through its normal compare-and-swap workflow.
Subsequent annotated revisions must use the live Overhead head as the source for surgical edits.
Reconcile accepted changes into the editable sources so the next rebuild preserves them.
