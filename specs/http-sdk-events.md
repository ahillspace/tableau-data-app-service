# HTTP, browser SDK, and event boundaries

Status: proposed interface contract for review, not an implementation plan or acceptance record.

This specification owns the public HTTP routes, browser SDK surface, event ingestion, durable event delivery, cursors, and resynchronization boundary.

The service remains one internal deployment, and the HTTP routes are not a customer-facing onboarding or administration product.

## Requirements, recommendations, and assumptions

User requirements are a framework-independent browser SDK, one shared internal service, provider-independent examples, no secrets in the SDK, typed execution results, safe pagination, verified and deduplicated events, and a missed-delivery recovery contract.

The supported client context is a Tableau Data App whose viewer is already authenticated to Tableau, but Tableau browser state is not treated as proof of authority to this backend.

The future front door and trusted request adapter remain unresolved, so this document specifies the adapter boundary without choosing a browser credential, cookie, token, SSO flow, or registration workflow.

Recommendations are JSON HTTP routes for command and query operations, polling for persisted execution and event records, opaque server-side cursors, and at-least-once event delivery with client deduplication.

Recommended byte, page, and retention values are proposals for review and require implementation measurement.

No provider, browser, Tableau deployment, or front-door compatibility claim is verified by this proposal.

## Trust and transport rules

The future trusted adapter verifies request authority and constructs `TrustedContext` before calling app, execution, connection, or event-delivery modules.

The `appId`, `bindingId`, `requestId`, capability reference, connection ID, execution ID, origin, cursor, and idempotency key are identifiers or selectors and never establish authority by themselves.

The SDK never accepts a caller-selected `appId` or `bindingId` as an authority field, and the server never constructs trusted context from JSON or query parameters.

The SDK accepts an injected `fetch` implementation and an optional asynchronous request-header provider for the future front door integration.

The header provider is a transport hook only, and its value is not generated, stored, refreshed, or interpreted by the SDK as an authorization credential.

The SDK has no field for provider secrets, connection tokens, upstream account identifiers, or raw provider cursors.

CORS uses operator-configured exact origins and remains a browser transport rule rather than an authorization mechanism.
Expose Location, Retry-After and Idempotency-Replayed to allowed browser clients; allowed credential/header transport still depends on the deferred front door.

An allowed origin, app URL, connection ID, or event cursor does not prove the caller's app or binding.

The service does not set or read a Tableau session cookie as an external-service credential.

## HTTP envelope and versioning

The initial base path is `/v1`, and incompatible public changes require a new route version or an explicitly versioned capability contract.

Successful service responses use the shared `Result<T>` envelope with `ok: true`, `data`, and `requestId`.

Service errors use `ok: false` with the shared `Problem` fields and the request ID generated by the HTTP boundary before authentication.

Execution completion errors are resource data in `ExecutionView.error`; they are not confused with a failed HTTP request to read the resource.

The server returns JSON with an explicit content type and applies a finite body size limit before parsing request data.

The server rejects unknown top-level fields on every JSON command and query schema.
Capability input schemas also reject unknown fields unless an explicitly declared map field allows them; normalization/defaults are identical for validation and idempotency fingerprinting.

The service never returns raw provider response bodies, arbitrary provider URLs, credentials, stacks or raw external subject IDs.
The reviewed authorizationUrl and opt-in minimal account display label are explicit safe exceptions, never loggable authority or identity credentials.

## Routes

| Method and path | Purpose | Success |
| --- | --- | --- |
| `GET /v1/capabilities` | Return the current app's enabled capability descriptors after trusted-context and policy checks. | `200` |
| `POST /v1/executions` | Persist and admit one execution request. | `202` for new admission or `200` for idempotent replay. |
| `GET /v1/executions/{executionId}` | Read an authorized execution snapshot. | `200` |
| `POST /v1/executions/{executionId}/cancel` | Request cancellation and return the same persisted execution resource. | `202` when cancellation is pending or `200` when already terminal. |
| `POST /v1/authorization-attempts` | Begin delegated authorization or same-subject reconnect with `{providerId, connectionId?}`. | `201` with AuthorizationStart. |
| `GET /v1/authorization-attempts/{attemptId}` | Read an owner-scoped attempt. | `200` with AuthorizationAttemptView. |
| `POST /v1/authorization-attempts/{attemptId}/cancel` | Idempotently cancel a nonterminal attempt. | `200` with AuthorizationAttemptView. |
| `GET /v1/connections` | List owned delegated connections using an optional opaque cursor. | `200` with Page<SafeConnection>. |
| `GET /v1/connections/{connectionId}` | Read one owned delegated connection. | `200` with SafeConnection. |
| `POST /v1/connections/{connectionId}/disconnect` | Disconnect an owned delegated connection. | `200` with SafeConnection and remote cleanup status. |
| `GET /v1/provider-callbacks/{providerId}` | Process the initial supported OAuth query callback. | Generic safe completion page, never Result<connection>. |
| `GET /v1/events` | Read a bounded page from the caller's authorized event feed. | `200` |
| `GET /v1/events/resync` | Establish a current feed checkpoint for recovery after a gap or cursor expiry. | `200` |
| `POST /v1/provider-events/{providerId}/{endpointId}` | Receive a provider-specific event on a statically registered ingress. | Provider adapter-defined success acknowledgement. |

The connection module owns the domain behavior of these lifecycle routes, as specified in [connections.md](connections.md).
Begin returns one attempt per request; a transport-lost begin may be retried manually, but a new attempt supersedes and fences any existing nonterminal attempt for the same owner/provider/reconnect target, limiting orphaned attempts.
Connection-list pages are bounded to 100 items with 15-minute opaque cursors bound to the same owner, app policy and authority epoch.
Browser lifecycle routes cannot provision, rotate, disable or disconnect app-owned credentials; those are operator operations.
The callback supports only the initial documented query-response protocol; form-post or other callback variants require explicit reviewed routes.
Callback responses use no-store and no-referrer headers and fixed operator-reviewed return navigation, never caller-controlled redirects.
Protocol validation failures return a generic 400 page; duplicates/in-flight/unconfirmed exchanges return generic status without disclosing connection identifiers.
The callback endpoint is not a browser-authority endpoint, and correlation state cannot mint TrustedContext.

The provider-event route is authenticated by the provider's registered event verifier rather than a browser `TrustedContext`.

Provider and endpoint path segments select statically configured adapters only, and are not arbitrary network destinations or secret webhook URLs.

The service provides no generic webhook relay, arbitrary event publishing route, raw provider proxy, or client-selected callback URL.

## Capability discovery

`GET /v1/capabilities` checks the current trusted context, app enablement, capability binding, and safe provider metadata before returning descriptors.

A descriptor includes capability reference, description, input and output schemas, fixed identity mode, effect, pagination declaration, safe limits, and whether a connection is required.
For cursor pagination it includes required pageLimits.defaultSize and pageLimits.maxSize; non-paginated descriptors omit those fields.

Discovery makes no provider request, refreshes no credential, creates no connection, and does not promise that every provider-side resource is currently accessible.

The SDK exposes `discoverCapabilities()` and returns the schema-derived descriptor types as received from the versioned service.

## Execution requests and responses

`POST /v1/executions` accepts the shared `ExecutionRequest` including its optional top-level `page` object for cursor-paginated reads.

The `page` object contains only `cursor` and `pageSize`, and capability business input remains in `input`.

A write capability rejects pagination controls, and a non-paginated read rejects a cursor or page size.

The idempotency key is required for every request under the shared contract, including reads, but a read key deduplicates admissions rather than promising effect protection.

A new execution returns the persisted `ExecutionView` with `202 Accepted`, a `Location` header, and a bounded `Retry-After` suggestion for polling.

An equivalent replay returns the existing snapshot with `200 OK` and `Idempotency-Replayed: true`.

A key reused for a different normalized effective request returns `409 CONFLICT` and creates no execution.

A transport failure after submitting a POST is resolved by resubmitting the exact request with the same key, never by generating a new key for a possibly accepted write.

The SDK exposes `submitExecution(request)`, `getExecution(id)`, `cancelExecution(id)`, and `waitForExecution(id, options)`.

`waitForExecution` polls the persisted resource with bounded backoff and stops at a terminal state, caller deadline, or abort signal.

Aborting `waitForExecution` stops the wait only and does not imply that the underlying execution was cancelled.

The caller uses `cancelExecution` when it intends to request cancellation.

The SDK does not hide an ambiguous submission by generating a replacement key, and retrying a POST is permitted only with the same request and key.

A convenience `execute(request, options)` may compose submit and wait, but it uses the same durable resource and must expose its idempotency key and execution ID for recovery.

## Execution access checks

Every execution read, idempotency replay, and cancellation request checks the current trusted app and binding, current app enablement, exact capability binding, current ownership of the original connection, connection state, and current authorization for the original identity.

The execution record captures the original SafeConnection.revision, which changes on grant replacement, permissions and lifecycle changes but not routine same-grant credential rotation.
A different external subject or delegated owner requires a new connection ID.

A result is disclosed only if the currently authorized connection matches the execution's original logical connection revision.

If the app capability binding or execution ownership has been revoked, the service returns `NOT_FOUND` and does not expose cached input or output.

If the caller still owns the execution but its connection now requires reauthorization, is disconnected, or has a different logical revision, the service returns a safe authorization error without the cached result.

A fresh credential token for the same logical connection does not by itself invalidate a previous result, provided current capability authorization and connection state remain valid.

This check prevents a result read or idempotency replay from disclosing data after a delegated account is replaced or its authority is revoked.

## Cursor pagination

Cursor pagination is allowed only for read capabilities whose output schema is a `Page<T>`.

A page response contains bounded `items` and an optional opaque `nextCursor` generated by the service.

The provider's native cursor is never sent to or accepted from the browser.

The service stores the provider cursor server-side under a cryptographically random client token or an equivalently protected opaque handle.

A cursor record is bound to app, binding, authorityEpoch, capability version, logical connection revision, normalized base input, page size, and expiry.
Every cursor resolution compares its epoch to the current context and deployment epoch, including connectionless reads; mismatch returns CURSOR_EXPIRED without provider I/O.

Using a cursor requires a new trusted context and a fresh policy and connection authorization check.

Changing the base input, capability, page size, binding, or logical connection revision invalidates the cursor and returns a safe input or authorization error.

An expired server cursor returns `CURSOR_EXPIRED`, while a provider-rejected stale cursor returns `RESYNC_REQUIRED` so the caller can restart from the first page.

A page execution has its own required idempotency key, and replaying a page request with the same key returns its existing execution rather than advancing the provider cursor twice.

The SDK treats cursors as opaque strings and provides `submitExecution` with page options rather than parsing provider pagination state.

Recommended page limits are a default of 50 items and a maximum of 100 items, with stricter capability-specific bounds allowed.

## Stable HTTP error mapping

| Error code | HTTP status | Client action |
| --- | --- | --- |
| `INVALID_INPUT` | `400` | Correct the request and use a new idempotency key if its intended operation changes. |
| `UNAUTHENTICATED` | `401` | Re-establish authority through the configured front door. |
| `FORBIDDEN` | `403` | Stop; do not change identity or retry automatically. |
| `NOT_FOUND` | `404` | Treat the resource as unavailable without probing alternate IDs. |
| `CONNECTION_REQUIRED` | `409` | Complete the supported connection flow, then submit a new intended operation. |
| `REAUTHORIZATION_REQUIRED` | `409` | Reauthorize the same logical connection before a new execution. |
| `UNSUPPORTED` | `422` | Use a capability or credential strategy declared as supported. |
| `CONFLICT` | `409` | Resolve the idempotency or concurrent configuration conflict. |
| `RATE_LIMITED` | `429` | Respect `retryAfterMs` and preserve the original key for the same request. |
| `PROVIDER_UNAVAILABLE` | `503` | Follow the error's retry advice and execution state. |
| `DEADLINE_EXCEEDED` | `504` | Inspect the execution, especially for a write that crossed dispatch intent. |
| `CANCELLED` | `409` | Read the terminal execution resource. |
| `OUTCOME_UNKNOWN` | `409` | Inspect or reconcile the original write; do not blindly resubmit. |
| `CURSOR_EXPIRED` | `410` | Restart pagination from the first page. |
| `RESYNC_REQUIRED` | `410` | Establish a new event checkpoint or restart the provider read. |
| `INTERNAL` | `500` | Use the request ID for safe operator diagnostics. |

A terminal execution state is returned as `200 OK` from its read route even when its `ExecutionView.error` contains an allowed Problem code; failed is an execution state, not an error code.

The response status mapping is stable across providers, while provider-specific details remain behind safe error codes and request IDs.

## SDK surface

The browser SDK is framework-independent and implements no account login, provider protocol, credential storage, Tableau session extraction, or front-door token minting.
Its connection helpers call the service and expose the reviewed authorization URL so the host can open the supported browser flow.

```ts
type ClientOptions = {
  baseUrl: string;
  fetch?: typeof fetch;
  requestHeaders?: () => Promise<Record<string, string>>;
};
type SubmitExecutionOptions = {
  capability: CapabilityRef;
  input: unknown;
  connectionId?: string;
  idempotencyKey: string;
  page?: { cursor?: string; pageSize?: number };
};
type ExecutionClient = {
  discoverCapabilities(): Promise<CapabilityDescriptor[]>;
  submitExecution(request: SubmitExecutionOptions): Promise<ExecutionView>;
  getExecution(id: string): Promise<ExecutionView>;
  cancelExecution(id: string): Promise<ExecutionView>;
  waitForExecution(id: string, options?: WaitOptions): Promise<ExecutionView>;
  beginAuthorization(request: { providerId: string; connectionId?: string }): Promise<AuthorizationStart>;
  getAuthorizationAttempt(id: string): Promise<AuthorizationAttemptView>;
  cancelAuthorization(id: string): Promise<AuthorizationAttemptView>;
  listConnections(options?: { cursor?: string }): Promise<Page<SafeConnection>>;
  getConnection(id: string): Promise<SafeConnection>;
  disconnectConnection(id: string): Promise<SafeConnection>;
  listEvents(options: { cursor: string; pageSize?: number }): Promise<EventPage>;
  resyncEvents(): Promise<{ baselineCursor: string }>;
};
```

WaitOptions contains a finite deadline, an optional AbortSignal and bounded polling interval; no local timeout claims to cancel the server execution.

The SDK unwraps successful Result.data and throws ServiceError carrying the complete safe Problem for a service error envelope.
Network failures and malformed/version-incompatible responses throw TransportError with requestId when available and a submissionMayHaveBeenAccepted flag for POST uncertainty.
A terminal ExecutionView.error remains returned resource data and is never thrown as an admission error.
The SDK preserves the caller's original idempotency key for recovery and does not retry malformed protocol responses blindly.

The SDK validates only transport-level constraints that can be known locally, and the server remains authoritative for schemas, policy, limits, and cursor binding.

The SDK never automatically retries a POST with a new idempotency key.

It may retry an identical execution-submission POST with the same key after a transport failure because admission is idempotent within the published retention window.
This rule does not authorize automatic retries of beginAuthorization, which has no idempotency key and is manually restarted through its supersession rule.

The SDK may retry idempotent GET requests with bounded backoff and honors server rate-limit guidance.

Polling and event consumption are explicit calls, and the initial SDK does not hold a background connection open.

The SDK returns typed provider-neutral execution and event envelopes; provider capability types are generated from or derived from the registered JSON schemas.

The SDK does not persist event or page cursors in browser storage by default, and the host app chooses whether and where to checkpoint them.

## Provider event verification and durable handoff

Only a statically registered provider event adapter accepts a provider event route.

The adapter verifies the original request bytes, provider-specific signature or authentication, timestamp and replay rules, endpoint configuration, size limits, and normalized event schema according to the provider's official protocol.

An endpoint ID is a routing selector rather than proof of authenticity, and event payload fields never choose an arbitrary app, binding, connection, provider host, or capability.

The provider adapter maps verified events to a stable provider event ID, normalized event type, safe event data, and a server-resolved connection reference.

A provider that cannot supply a stable event identity must declare and test a provider-specific deduplication rule before its events are enabled.

The service inserts the verified inbox record and all authorized feed delivery records in one Postgres transaction.
The event transaction locks affected app rows, connection rows and feed heads in that order, sorting IDs within each group; this matches execution/connection policy lock order.
Each feed has a transactional head row; appenders assign positions and update heads in the same transaction as delivery insertion.
A committed head cannot exceed an uncommitted earlier position in that feed; a sequence value or MAX(eventId) is not a valid committed watermark.
Deadlock/serialization failures roll back the whole inbox-and-delivery transaction and retry with the same verified source key under bounded ingress deadlines.

The HTTP ingress acknowledges success only after that transaction commits, and a duplicate event with the same provider, endpoint, and provider event ID is acknowledged without creating another feed entry.

A verification, schema, mapping, or persistence failure is not acknowledged as accepted, allowing the provider's documented retry behavior to operate.

The service stores only normalized allowlisted event data and safe source metadata, never raw signatures, credentials, full unredacted bodies, or account identifiers.

Provider events are notifications and do not themselves authorize capability execution or mutate an unrelated business workflow.

The initial core does not execute arbitrary workflows, call user-selected callbacks, or deliver events directly to a browser using an inbound provider connection.

## Event audience and delivery

AppRegistration.eventSubscriptions declares allowed versioned event types, connection IDs and audiences before an event can enter a client feed.
The event registry validates a data schema and current-state resync capability for each event definition; app policy must enable that read capability.
For an app audience, one app feed row is visible to its currently authorized bindings; for connection_owner, a delegated owner feed is scoped to exactly one app/binding pair.
The browser sees a logical combined feed; its opaque cursor contains server-side positions for each currently authorized feed and the subscription revision.
Current-state resync capability authorization, original connection revision, binding validity and app policy are rechecked before payload delivery; revoked entries are skipped without disclosing their data.

Delegated connection events are scoped to the owning app and binding.

App-credential event types require an explicit app-level audience rule, and are never implicitly broadcast merely because a connection is shared by an app.

A caller with no current authority for the event's app, binding, connection generation, or event subscription cannot read that event.

`GET /v1/events` returns a bounded page of normalized `EventEnvelope` items and a new opaque feed cursor.

Delivery is at least once, so a client may receive a previously returned event again after a lost response or checkpoint.

Every event has a stable service `eventId`, and the SDK consumer deduplicates repeated IDs within its own handling policy.

The consumer should persist its next cursor only after it has handled the returned events, so a client crash can cause a repeat but not a silent checkpoint past unhandled events.

A cursor is scoped to app, binding, authorityEpoch, event subscription revision and feed positions, and cannot be used as authority outside those checks.
An event cursor epoch mismatch returns RESYNC_REQUIRED without event payloads.

The outbox is a durable delivery boundary in the same Postgres deployment, not a new queue service or workflow engine.

The initial delivery transport is authenticated polling; server-sent events or other push delivery may be added later without changing event identity, authorization, or resync semantics.

## Missed delivery and resynchronization

The caller uses `GET /v1/events/resync` to obtain an opaque baseline cursor at the committed heads of its currently authorized feeds.
Read the feed heads and subscription revision in one consistent database snapshot; concurrent lower-position commits cannot appear behind this baseline under the head-lock protocol.

The caller then re-reads relevant current state through ordinary authorized discovery, connection, execution, or capability APIs before polling events after that baseline.

Events are hints and the provider or application API remains the source of current state.

A new cursor or cursor whose position is older than retained feed data returns `RESYNC_REQUIRED` with no event payload.

The client obtains a new baseline, rebuilds the state it needs through currently authorized APIs, then resumes polling from the baseline cursor.

Events committed after baseline creation are available after that cursor.
Canonical reads rebuild current state only to the extent the provider read API supports it; the generic service does not promise a provider-wide snapshot, immediate consistency or ordered upstream events.
Clients treat notifications as invalidation hints and may reread state when the provider is eventually consistent.

The generic service does not promise to reconstruct provider state that has no corresponding authorized capability or canonical read API.

Proposed initial retention is seven days for normalized event payloads and feed positions, subject to deployment review.
Source-event deduplication tombstones are separate and persist at least the adapter's documented maximum redelivery age plus clock tolerance; payload pruning cannot delete these keys early.
An adapter without a bounded redelivery age is unsupported for initial event ingestion unless an explicit durable-deduplication policy is approved.
Replays beyond the declared provider horizon do not carry the within-horizon deduplication guarantee and are rejected when event age can be verified.
Expired pagination cursors use a proposed 15-minute TTL independent of event feed retention.

The server must return `RESYNC_REQUIRED` rather than silently skip an expired or pruned position.

## Synthetic traces

### Cursor-paginated delegated read

Binding `binding-7` submits `sample-alpha.lookup@1` with normalized filter `{region: "north"}`, page size `25`, and idempotency key `page-1`.

The provider returns 25 safe items and a native cursor, which the service stores against the app, binding, capability, logical connection revision, filter, and expiry.

The service returns an opaque `nextCursor` that reveals no provider cursor, and the SDK submits it with the same filter and a new idempotency key for the next page.

Changing the filter while reusing that cursor returns `INVALID_INPUT`, and reauthorizing the connection as a different external subject invalidates the cursor.

### Verified and replayed provider event

A synthetic `sample-alpha` event arrives at the registered endpoint with event ID `evt-204`.

The provider adapter verifies its signature and schema, resolves the server-owned delegated connection, and the service commits one normalized event and one authorized binding-scoped outbox row.

The provider retries `evt-204` after losing the acknowledgement, and the unique source event key causes a successful duplicate acknowledgement without a second client feed entry.

Binding `binding-7` polls the feed, processes service event ID `event-88`, and checkpoints the returned cursor only after handling it.

A different binding cannot read the event by guessing `event-88` or copying the cursor.

### Lost event cursor

The browser returns after the seven-day event cursor retention window and receives `RESYNC_REQUIRED`.

The SDK asks for a new baseline cursor, the app re-reads current safe connections and known execution states, and then resumes polling after the baseline.

The service does not claim that this procedure reconstructs arbitrary provider history or creates a workflow replay.

## Acceptance scenario coverage

The configured Data App capability discovery scenario is covered by `GET /v1/capabilities` with current app policy checks.

The no-credential, explicit app-credential, and delegated execution scenarios use the same execution route and fixed capability identity mode.

The connection-ID guessing and cross-binding scenarios are blocked by current trusted-context, owner, policy, and connection checks on every route.

The paginated read and write scenarios use the same persisted execution and SDK surface, with server-bound pagination cursors only for declared reads.

The event acceptance scenario verifies provider authenticity, deduplicates before feed insertion, scopes delivery, and exposes resynchronization after cursor expiry.

The front-door, browser transport, and Tableau Cloud or Server compatibility scenarios remain unresolved until an adapter and target deployment are selected and verified.

Implementation verification and user acceptance remain pending because this workspace contains proposals only.
